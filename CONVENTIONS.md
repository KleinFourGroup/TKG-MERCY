## Baseline workflow

- **Run `./Scripts/python.exe -m smoke` at the start and end of any invasive step.** All checks in the `smoke/` package are the always-on regression net. Start-of-step confirms you're building on a clean base; end-of-step confirms you didn't break anything before you commit. Offscreen, fast (~few seconds total), so there's no excuse to skip it. Each check function carries a docstring describing what it covers — that's the live source of truth (the historical list in [`plan_archive/test_conventions.md`](plan_archive/test_conventions.md) is frozen at the eleven checks present at the 2026-04-22 split, and predates the 2026-05-11 split of `smoke.py` into a package).
- **The real DB for real-data drills is `Mercy 2.0 DB 7-8-26.db`** in Matthew's home dir (`C:\Users\mkilg\`), MERCY's default DB directory. It **supersedes `Mercy DB 6-1-26.db`**, which older §13 narratives name — the team rolls the date forward, so sanity-check for a newer `Mercy*.db` by mtime rather than trusting this filename. **Always work on a COPY:** opening a MERCY DB migrates it in place and commits, so never point the app or a driver at the original. Two pitfalls: real presses have **no mounted die** (`Press.currentPart` unset), so any hysteresis drill must synthesize a mount; and a driver that commits through an edit window pops a modal `QMessageBox` that **hangs forever headless** — call `smoke.ui._silenceMessageBoxes()` first. Drill drivers are deliberately uncommitted (machine-specific), so you write a throwaway each time.
- **Keep `fuzz_db.py` in sync as `records.py` / the schema evolves.** When a new record type lands or an existing one gains fields, update the fuzz generator so it continues to produce fully-populated DBs. Cataloged in `MERGE_PLAN.md` §13.8 as landed, but the tool is a live dependency of any report-stress or migration-rehearsal work — let it rot and the generated DBs quietly diverge from the real schema.

## Gotchas

- **Every edit path calls `mainApp.refreshAllViews()` — never hand-wire a refresh.** Since Step 81 there is exactly one repaint call on every edit/delete success path, and it repaints *every* tab (~10 ms on the real DB). **Do not** add `mainApp.someTab.refreshTable()` fan-outs when you add an FK: that hand-wiring grows O(FK-edges), and forgetting one leaves a *distant* tab silently stale — the bug Step 81 retired after it recurred across Steps 48/64/74a/79. A new FK edge needs **no** refresh wiring at all. Two entry points: `refreshAllViews()` (post-edit; preserves picker selections, leaves a generated schedule alone) and `_refreshAllTabs(hard=True)` (DB load; hard-resets pickers, clears the schedule) — don't call the latter from an edit path.
- **Tab-level pickers must preserve their selection by key, not by label.** A tab whose sub-tabs key off a dropdown (Employees → Overview, Inventory) is repainted on *every* edit, so a rebuild that resets to index 0 would yank the user's drill-down away mid-read. Follow `production_tab._populateEmployeeFilter`: stash the current key, `blockSignals` across the rebuild, carry the key as `addItem(..., userData=key)`, re-find it, fall back to index 0 only if the record genuinely vanished. **Match on the stable key, never the display string** — a rename rewrites the label, and renames are exactly when a stale view bites. And since `blockSignals` suppresses the rebuild signal that normally repaints the dependent sub-tabs, drive that sync explicitly once after the rebuild.
- **Smoke fixtures must build *valid* DBs — use `db.addX()`, not raw dict inserts.** Because every tab renders on every edit (Step 81), a fixture that inserts `db.mixtures[name] = Mixture(...)` directly skips the `db` back-reference that `addMixture()` sets, and `Mixture.getCost()` raises the moment any edit repaints the Mixtures tab. Step 81 found two such fixtures. Product code is fine (`file_manager/load.py` sets the back-ref explicitly after its direct insert; everything else goes through `addX()`), so this bites *tests* only — but it now bites them loudly.
- **Headless `Employee` construction.** `Employee.shift` is an `int` and `Employee.fullTime` is a separate `bool`. Set them as two fields (`e.shift = 1; e.fullTime = True`) or use `setJob(role, shift, fullTime)`. **Do not** pre-format the compound string (`e.shift = "1|1"`) — `Employee.getTuple()` re-appends `|{fullTime}` unconditionally and you'll end up with `"1|1|1"` on disk, which the migration path won't recognize as a legal shape.
- **Offscreen Qt needs a `QApplication`.** Any throwaway `./Scripts/python.exe -c '...'` that touches a Qt widget (including `MainWindow()`) must construct `QApplication([])` first. Otherwise Qt aborts silently during widget construction and bash reports exit 127 — which *looks* like "command not found" and sends you hunting for the wrong bug. The `smoke/` package handles this for you (its `__init__.py` sets `QT_QPA_PLATFORM=offscreen` before any Qt import); standalone probes need the boilerplate.
- **Never format an integer count with `:g`.** `f"{n:g}"` is 6-significant-digit *general* format, so it silently flips to scientific notation past 999999: `f"{1234567:g}"` → `'1.23457e+06'`. It's invisible in testing (fixtures are small) and only corrupts on real, large data. Step 82 found it live on the schedule's Quantity and `OrderFlag.piecesShort` cells, where a 1.2M-piece order would have rendered as garbage. Use `:,` for counts (and you get thousands separators free); reserve `:g` for genuine floats where you want `76` rather than `76.0` (e.g. `OrderFlag.shortHours`). Same trap applies to any count rendered into a tab cell or a PDF table.
- **New tables go in via migration — never into the format fingerprint.** When adding a table (e.g. the Production Scheduling tables from Step 43 on), bump `MERCY_DB_VERSION`, add a `CREATE TABLE IF NOT EXISTS` to `_createSchedulingTables()` (the fresh-schema path: empty / legacy ANIKA / legacy BECKY) **and** an additive idempotent `_migrate<N>To<N+1>()` for existing MERCY DBs (wired into the Case-2 chain in `file_manager/__init__.py`). **Do not** add the new table to `UNIFIED_TABLES` in `schema.py`: `_detectDbFormat` classifies a file as "mercy" via `UNIFIED_TABLES.issubset(tables)`, and a pre-bump MERCY file legitimately lacks the new table — requiring it would mis-classify older files as "unknown" and refuse to open them. The fingerprint stays frozen at the v4 shape. Also: bumping the version breaks any smoke migration check that hardcodes the *terminal* `db_version` (legacy ANIKA / legacy BECKY / the latest `mercy_vN_to_vN+1`) — update those literals as part of the same step.

## Reports

- **Bold a totals row by passing it as headers to a zero-row table.** `PDFReport.drawTable` renders the `headers` argument in `Times-Bold`; data rows are plain. So the codebase's convention for emphasizing a "Total" line at the bottom of a section is `self.drawTable([], totalsRow)` — no data, totals list passed as headers. This sidesteps needing a bold-data-row knob on `drawTable`. Used in every production report (`productionSummaryReport`, `productionActionReport`, `productionTargetReport`, `productionEmployeeReport`, `productionProductivityReport`). If you add a new report and want a bold totals row, reach for this first before adding a new API.

## Versioning & builds

- **Don't hand-edit a version constant.** `app.py` imports `VERSION` from [`version.py`](version.py), which shells out to `git describe --tags --always --dirty` at import time. Clean tag → `1.0rc3`; past the tag → `1.0rc3-2-gabc1234`; dirty tree → `-dirty` suffix. Leading `v` is stripped so tags like `v1.0rc3` render as `1.0rc3`.
- **Release flow is just `git tag vX.Y.Z && git push --tags`**, then `pyinstaller main.spec`. The spec runs the same `git describe` at build time, writes `_version.py` (gitignored, bundled into the exe as the frozen-mode fallback), and names the output `mercy-{VERSION}.exe`.
- **`_version.py` is auto-generated.** Never edit it — `main.spec` overwrites it on every build. If it's missing in dev and git is also unavailable, `version.py` returns `"dev-unknown"`.
- **`main.spec` is tracked** (carved out of the `*.spec` ignore with a `!main.spec` rule in `.gitignore`). Edit it when the build pipeline needs to change; don't `.gitignore` it again.
